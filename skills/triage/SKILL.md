# Triage

Move issues on the project issue tracker through a small state machine of triage roles.

**Tracker:** GitHub, `joshualongenecker/home-assistant-bridge-esphome`, via the `gh` CLI. Resolve a bare `#42` against that repo.

**Permission note:** the session's `gh` account may have pull-only access to the tracker. Reading issues always works. Applying labels or posting comments requires triage/write permission — when the account can't write, do the full triage work (analysis, grilling, brief) and present the label changes and comment text for the user to apply, instead of silently skipping them.

Every comment posted to the tracker during triage **must** start with:

```
> *This was generated by AI during triage.*
```

## Roles

Two **category** roles (existing labels): `bug`, `enhancement` (also `documentation`).

Six **state** roles (factory labels):

- `needs-triage`: maintainer needs to evaluate
- `needs-info`: waiting on reporter for more information
- `accepted`: triaged, worth doing, not yet specified
- `ready-for-agent`: spec and tickets exist, ready for an agent session
- `in-progress`: actively being worked
- `needs-device-verify`: code review clean; test-bench verification outstanding before PR

Terminal: `wontfix`, `duplicate`, `invalid` (close the issue).

Every triaged issue carries exactly one category role and one state role. If state roles conflict, flag it and ask before doing anything else.

State transitions: unlabeled → `needs-triage` → `needs-info` | `accepted` | terminal. `needs-info` → `needs-triage` when the reporter replies. `accepted` → `ready-for-agent` (after `grill-with-docs` + `to-spec` + `to-tickets`). `ready-for-agent` → `in-progress`. `in-progress` → `needs-device-verify` (firmware-facing changes only) → `in-progress` (verification failed) or PR opened (labels cleared on merge). The user can override at any time; flag unusual transitions and ask before proceeding.

## Invocation

The user invokes `/triage` in natural language: "Show me anything that needs my attention", "Let's look at #42", "Move #42 to ready-for-agent", "What's ready for agents to pick up?"

## Show what needs attention

Query the tracker and present three buckets, oldest first:

1. **Unlabeled**: never triaged.
2. **`needs-triage`**: evaluation in progress.
3. **`needs-info` with reporter activity since the last triage notes**: needs re-evaluation.

Show counts and a one-line summary per item. Let the user pick.

## Triage a specific issue

1. **Gather context.** Read the full issue (body, comments, labels, author, dates). Parse prior triage notes so you don't re-ask resolved questions. Explore the codebase using `docs/GLOSSARY.md` vocabulary, respecting ADRs in `docs/adr/` in the area. Run two checks: (a) **redundancy** — search for an existing implementation of the requested behavior by domain concept (not just the request's wording) and report where you looked; if found, it's a `wontfix` (already implemented, point to where it lives). (b) **prior rejection** — check closed issues with similar scope.

2. **Recommend.** State your category and state recommendation with reasoning, plus a brief codebase summary relevant to the request (including whether it's already implemented). Wait for direction.

3. **Verify the claim.** Before any grilling, check that the claim holds up. For a bug, reproduce it from the reporter's steps — run the relevant `make test` / `make integration-test` / simulation test, or trace the code path. Report: confirmed (with code path), failed, or insufficient detail (a strong `needs-info` signal).

4. **Grill (if needed).** If the request needs fleshing out, run a `grilling` session with `domain-modeling` active (the `grill-with-docs` skill), one round at a time, updating `docs/GLOSSARY.md` and `docs/adr/` inline as decisions land.

5. **Apply the outcome:**
   - `ready-for-agent`: post an agent brief comment (template below).
   - `needs-info`: post triage notes (template below).
   - For `wontfix`, close with a comment explaining why (already implemented / rejected / duplicate of #N).
   - `needs-triage` / `accepted`: apply the role; optional comment if there's partial progress.

## Agent brief template

```markdown
## Agent Brief

**Goal:** <one sentence, in glossary terms>

**Context:** <what the codebase does today in this area; cite modules/specs>

**What to build:** <the end-to-end behaviour, from the user's perspective>

**Constraints:** <invariants from .github/copilot-instructions.md that apply, ADRs that bind, specs that must be updated>

**Acceptance criteria:**
- [ ] ...

**Verification:** <which test targets must pass; device-verify required? (firmware-facing changes touch components/ or lib/)>
```

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1
- point 2

**What we still need from you (@reporter):**

- question 1
- question 2
```

Capture everything resolved during grilling under "established so far" so the work isn't lost. Questions must be specific and actionable, not "please provide more info".

## Quick state override

If the user says "move #42 to ready-for-agent", trust them and apply the role directly. Confirm what you're about to do (label changes, comment, close), then act. Skip grilling. If moving to `ready-for-agent` without a grilling session, ask whether they want an agent brief written.

## Resuming a previous session

If prior triage notes exist on the issue, read them, check whether the reporter has answered any outstanding questions, and present an updated picture before continuing. Don't re-ask resolved questions.
